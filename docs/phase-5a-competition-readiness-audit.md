# TrustTrail — Phase 5A competition readiness and independent judge audit

Audit date: 3 November 2026, Asia/Jakarta. Scope: current local implementation and production preview. **Audit only: application source, gameplay, scoring, persistence, deployment and Git were not changed.** New files are audit documentation and non-sensitive test evidence. Production build artifacts were regenerated by the requested build check.

## 1. Executive summary

**Verdict: playable and suitable for a controlled local demonstration; not yet signed off for official submission.** All three chapters, unsafe choices, exposure-specific recovery, and the final report work in the tested Chromium environment. The strongest feature is careful teaching: a different domain is a reason to verify, HTTPS is not identity, opening a link does not automatically mean compromise, and earlier identity exposure remains relevant after later safe decisions.

The largest risks are release evidence and reproducibility, not missing visual effects. The original competition guide is unavailable; no public deployment, team-leader repository or demo-video submission link was located in the reviewed documentation. These are **two P0 readiness gates with unverified external status**, not two proven runtime failures or proven rule violations. The declared ESLint version is incompatible with the lint configuration, and `npm run check` fails. Browser regression results also require qualification (section 14).

The report accurately describes actual actions but weakly translates missed checks into a personal improvement plan. Recovery wrong answers are temporary feedback, absent from the durable history. Explicitly labeled inspection actions and mandatory Chapter 3 comparison teach the procedure but do not independently establish transfer to an unfamiliar scam.

**Internal category diagnostic: 74.8/100, unweighted. Official weighted competition score: unavailable.** Official weights could not be verified and therefore were not used. This is a critical assessment of present evidence, not a prediction of competition placement.

Issue register: **P0: 2 readiness gates; P1: 1; P2: 6; P3: 1.** No demonstrated critical scoring corruption or broken core playthrough was found.

## 4. Theme alignment

Actual gameplay meaningfully addresses deception rather than presenting a passive awareness page. It puts an unemployed graduate under plausible recruitment pressure, then combines unsolicited opportunity, personal rapport, channel migration, unnecessary identity requests and account-code theft. Actions produce differentiated consequences; unsafe choices remain recoverable. Independent verification is taught explicitly, with limitations rather than automatic fraud labels.

The first screen identifies the product as a digital-security investigation game and explains the recruitment premise. The fictional simulation and no-account boundary are visible. The scope is narrow—one connected recruitment trap—yet coherent. No evidence supports claiming broad scam-detection ability or improved real-world behavior. The game itself appropriately avoids such certification claims.

### Recovery

Four base actions: stop interaction, preserve private evidence, confirm through an independently found company contact, and report to platform. Account exposure adds official account recovery, foreign-session removal, password/recovery/forwarding/MFA checks. Identity exposure adds official issuer help and monitoring. Financial loss is not invented; payment-provider guidance is conditional. These are useful, proportionate real-world concepts, but the game supplies no specific verified local reporting pathway. Wrong choices receive explanations and can be corrected immediately. No real reports, account changes or uploads occur.

Architecture separates typed content, a pure reducer, state/actions contexts, persistence and OS presentation. Invalid/stale/repeated actions preserve reducer identity; save replay validates permitted transitions. Persistence is bounded at 128 KiB and 1000 events and rejects unknown fields/version mismatches. Storage failures and cross-tab conflicts have user-facing recovery. This is stronger than trusting a serialized score object. The central OS component has many presentation responsibilities and compressed JSX makes review harder, but no rewrite is needed for competition readiness.

No error boundary was found in `main.tsx`/`App.tsx`. Content validation and specific renderer/storage failure handling reduce known risks; no actual uncaught production crash was demonstrated. Treat adding a general fallback as optional hardening, not a claimed critical vulnerability.

### Measurements, not performance promises

Vite reports entry JS **541.38 kB / 168.26 kB gzip**, CSS **112.65 kB / 22.06 kB gzip**, lazy city scene **251.62 kB / 74.30 kB gzip**. One unthrottled local 1440×900 Chromium sample after two seconds recorded LCP 260 ms, CLS 0, approximately 1,321,518 resource-transfer bytes, 11 long tasks of 68–447 ms, and city `ready/running`, resolution 1. See `probes.json`.

This single local run used headless Linux Chromium while other audit work was active. Long tasks are a risk signal, not attribution to Pixi, Motion or React. No FPS, mobile-device speed, field Core Web Vitals, INP or performance improvement is claimed. Before submission, repeat under representative CPU/network conditions, with motion running/paused/reduced and without concurrent audit load (F10).

Pixi code explicitly owns and destroys app, textures, observers/listeners and ticker; handles abort/init races and lost rendering; pauses for visibility and preference changes. Browser tests exercise fallback, missing layers, renderer failure and repeat navigation. This supports cleanup correctness in tested cases, not a general GPU-memory-leak certification.

### Security/privacy assessment

No exploitable critical application vulnerability was demonstrated in the reviewed paths. Authored React content is rendered as text; targeted search found no `dangerouslySetInnerHTML`, `eval` or application `innerHTML` sink. Simulated destinations use `.example` and remain inert; sensitive input/upload/payment forms are absent. No telemetry or gameplay API is required. Browser safe-route tests assert no external gameplay requests; intelligence source links intentionally leave the site when activated.

Local saves are validated as untrusted input but are editable by the browser owner. They are not tamper-proof examination results; this is acceptable for a self-guided educational game and should not become an authentication/competition-proof mechanism. The read/compare/write cross-tab guard is not a transactional database; concurrent-write races remain a general limitation rather than a reproduced loss in this audit.

Public TLS, response headers, caching, public repository hygiene and deployment logging cannot be evaluated without a deployment/repository link. No missing production header or live-site security defect is asserted from the local preview. No registry vulnerability database scan or clean dependency installation was performed; no dependency-security clearance is implied.
